# 第二大腦工作台改版計畫：精簡核心、知識資料夾、附件

把工作台做成「核心極簡、資料夾就是與其他系統的接點」的本機工具。專案／任務／長期知識／附件都在同一個資料夾；人和 AI 都能快速找到。本文件是分段 session 的唯一路線圖。

每次開一個 session **只做一項**、分別 commit；本機確認後再考慮下一個 session。不要在同一個 session 混做下一項。不要 push 到公開遠端，直到該階段測試通過、文件與示範 vault 一致。

相關現況：`docs/architecture.md`、`docs/readability-roadmap.md`、`packages/brain-core/src/scaffold.ts`、`packages/brain-core/src/vault-index.ts`、`apps/desktop/src/vault.ts`。

## 外掛生態：適合，但不是現在拿來開源的那張牌

**這個專案將來適合讓人做外掛。開源第一版不適合把「外掛平台」當主功能。** 兩句都要成立，不要聽成「永遠不准擴充」。

生態系確實能讓工具變強。VS Code、Obsidian、Chrome 都是這樣。但它們的外掛是在**已經有人每天打開**之後才爆發的。開發者為「我已經在用的主程式」寫套件，不會為一份還沒做完核心、README 卻在招募外掛的 0.x 專案寫套件。很多新興專案一開始就做 Plugin API，最後是空的 `plugins/` 資料夾，不是生態。

更硬的一點：若把成功押在「自由開發外掛」上，你會去跟 Obsidian 搶同一種生態。對方已經有成千上萬套件。你比較贏的是另一件事——**同一資料夾上，工作台管今天與時間，AI 靠 INDEX 接上，不必重講。** 這條路上，別人現在就能擴充：寫 Obsidian plugin、寫 AI skill、寫腳本，都是讀你的 Markdown。那也是生態，而且你不必養執行期、權限、商店。

所以分三層，不要混：

| 層 | 何時 | 誰來擴充 |
| --- | --- | --- |
| 資料夾契約（Markdown、INDEX、路徑） | **現在就做，而且要凍得住** | 任何編輯器、AI、腳本、將來的外掛 |
| 別人的系統（Obsidian、Claude、雲端資料夾、提示詞 JSON） | 開源第一版的故事 | 既有工具 |
| 應用內外掛（調色包、沙箱面板、第二種看板） | 核心被人每天用、且同一需求重複出現 | 社群 |

本計畫只做第一層，並把格式寫穩，等於替將來的外掛先打地基（plugin-ready），但不實作外掛執行期。重提應用內外掛的門檻：Session 1–8 完成、格式不再每周改、至少有真實使用者反覆要同一種核心不該做的功能。

## 目標

1. 預設安裝只有工作需要的東西：看今天、改時間、看專案進度、寫知識、掛檔案。
2. AI 先讀 `.ai/INSTRUCTIONS.md`，再讀短的 `.ai/INDEX.md`，再打開 **一個** 正文檔。
3. 專案／知識／日誌可加圖片與 PDF；檔在 `附件/`，md 只記相對路徑；軟體可預覽圖、一鍵開檔。
4. 開源時別人能用同一資料夾接上自己的編輯器與 AI。應用內外掛不是第一版的賣點。

## 非目標（全程不要做）

- 預設「一個專案一個資料夾」或「一篇知識一個資料夾」。
- 自動產生 `10-`、`20-` 編號或檔名流水號。
- 內建 PDF 閱讀器、把 PDF 當知識正本、把檔案 base64 塞進 Markdown。
- 桌面程式內建大型 LLM。
- 本計畫不做應用內外掛執行期、外掛商店、主題包引擎、從網路抓知識（將來可另開計畫）。
- 把真實使用者 vault、個人路徑、憑證寫進 git。

## 核心必須極簡

主選單只留：今日、日曆、看板、專案、知識、設定。

| 核心負責 | 為什麼 |
| --- | --- |
| Markdown 任務／專案／知識格式 | 長期正本；也是給 Obsidian 與 AI 的契約 |
| 原子寫入、備份、canonical root | 安全與復原 |
| 今日／日曆拖時間 | 基本便利 |
| 一個預設看板 | 預設體驗乾淨 |
| INDEX 產生 | 機器地圖必須確定 |
| 亮／暗色 | 已有就夠 |

調色盤、第二種看板、抓網頁、行業流程：**不加進核心。** 需要時用 Markdown、AI，或別的 App 讀同一個資料夾。

## 目標磁碟外形

軟體**寫入**只走這套。舊的 `Projects/`、`Collections/`、`10-收件匣/`、`90-模板/` **仍要能讀**，直到搬家 session 完成。

```text
vault/
  .ai/                 INSTRUCTIONS.md（人寫）+ INDEX.md（機器產生）
  收件匣/               還沒歸檔的任務與靈感
    待辦.md
  日誌/                 每天會議與當日執行紀錄
    YYYY-MM-DD.md
  專案/                 一個專案一個 .md（不是一個資料夾）
  知識/                 一篇知識一個 .md；底下只有少數分類資料夾
    FAQ/
    產業/
    社群/
    影片/
    方法/
    提示詞/
  附件/                 圖片、PDF、其他檔；依專案名或知識分類分子夾
  模板/                 可套用模板（不當內容掃描）
```

對照使用：

| 使用者要做 | 軟體畫面 | 磁碟 |
| --- | --- | --- |
| 今天做什麼、改時間 | 今日／日曆 | 任務行在收件匣或專案檔 |
| 專案進度 | 專案 | `專案/*.md` |
| 長期筆記、常用知識 | 知識 | `知識/<分類>/*.md` |
| 會議與當天結論 | 今日結束寫入日誌 | `日誌/YYYY-MM-DD.md` |
| 圖片／PDF | 專案、知識、日誌頁「加入檔案」 | 複製到 `附件/…`，md 寫相對路徑 |
| 用別的工具看同一份資料 | Obsidian／編輯器／AI | 同一個 vault；先讀 `.ai/` |

三種知識是同一種筆記的生命週期，**不是三棵資料夾樹**：

- 常用：`知識/` 裡標 `importance: 1`，INDEX 列標題＋路徑。
- 當天產生：先寫 `日誌/`；值得留的再「存成知識」。
- 長期累積：軟體「新增知識」，進 `知識/<分類>/`。

任務與知識用 `[[wikilink]]` 互指，不把知識檔搬進專案資料夾。

## 開源時「配合別人的系統」指什麼

已經做、或做完本計畫就自然成立的，優先講這些，不要講外掛：

| 系統 | 怎麼接 |
| --- | --- |
| Obsidian、VS Code、任何編輯器 | 同一資料夾；普通 Markdown |
| Claude Code、Codex、其他 AI | `.ai/INSTRUCTIONS.md` + `.ai/INDEX.md` + 路徑 |
| 手機 | 資料夾放 OneDrive／Dropbox／Google Drive／Obsidian Sync，用手機 Markdown App（公開版不做內建雲同步） |
| AI 提示詞 Plus | 既有 JSON 匯入／匯出到知識（提示詞分類） |

本計畫**不加**：日曆 ICS 訂閱、瀏覽器剪藏器、Slack／Notion API、應用內外掛。那些是「有人每天用了再考慮」的清單，不是開源第一版的範圍。

開源要人願意試，靠的是：繁中／英文 README、sample-vault、今日改時間的畫面、以及「AI 不用你重講一遍」這句話是真的（INDEX 真的短、路徑真的對）。

將來若做應用內外掛，應長在穩定的資料夾契約上：只能經由正式 API 寫 Markdown，不能改編碼、不能碰 vault 外路徑、不能取代核心看板。那會是另一份路線圖，不是把這 8 個 session 塞爆。

## Session 1 — 正式資料夾契約

**現況：** 新增專案 → `Projects/<名>.md`；新增收藏 → `Collections/<名>.md`；新任務 → `10-收件匣/待辦收件匣.md`；模板在 `90-模板/`。掃描會讀到 `tmp/` 備份。

**改成：**

- `brain-core` 集中定義 canonical 相對路徑（`專案/`、`知識/`、`日誌/`、`收件匣/待辦.md`、`附件/`、`模板/`、`.ai/`）。
- **寫**只用新路徑；**讀**仍接受 `Projects/`、`Collections/`、`10-收件匣/`、`90-模板/` 與任何帶 `type: project|collection` 的 md。
- 內容掃描排除：`模板/`、`90-模板/`、`附件/`、`tmp/`、檔名含 `backup` 的目錄、技術／隱藏目錄（既有 `path_policy`）。
- 第一次建立知識架構與 `examples/sample-vault` 改成新外形。舊檔不覆寫。
- `path_policy` 的 managed 名單納入 `.ai`、`模板`、`90-模板`。`validate_relative_path` 本 session 仍可只准 `.md`（附件在 Session 6 再放寬）。

**測試：** scaffold 路徑、sample-vault 沒有把專案放根目錄、舊 `Projects/A.md` 仍掃成專案、`tmp/backup-…` 不再進 snapshot。

**完成標準：** 新 vault 新增專案出現在 `專案/`；打開仍用 `Projects/` 的舊 vault 專案還在。不要做知識 UI 文案大改（那是 Session 3）。

## Session 2 — 聰明 INDEX

**現況：** `.ai/INDEX.md` 重複編碼說明、專案表沒有路徑、未排程想法可含備份檔、沒有日誌／常用知識。

**改成：** INDEX 只當地圖。

必有：

- 進行中專案：名稱、狀態、進度、**路徑**
- 今日任務、逾期任務：標題、時間、專案、路徑
- 常用知識（`importance: 1`）：標題、分類、路徑
- 今日日誌路徑（檔案若存在）
- 未排程想法：很少、且已排除雜訊

移出 INDEX：完整編碼規格（改放 `.ai/INSTRUCTIONS.md` 或文件）、50 筆想法灌滿、備份重複列。

編碼規格可留在 INSTRUCTIONS 的短版「如何新增一行任務」。INDEX 結尾的 AI 操作說明改成：先 INSTRUCTIONS，再 INDEX，再只開列出的一個檔；不要讀整本收件匣。

**測試：** 同 snapshot 輸出穩定；專案列含 `專案/…` 或相容舊路徑；fixture 含 `tmp/backup` 時不出現。

**完成標準：** 產生的 INDEX 短到可當 AI 第一份地圖。不要在這次做附件。

## Session 3 — 知識庫介面

**現況：** 畫面叫收藏，定位接近提示詞；新增寫入 `Collections/`。

**改成：**

- 繁中主選單用「知識」；英文可維持 Collections 或改 Knowledge（選一個，測試跟著改）。
- 新增知識：名稱、分類（FAQ／產業／社群／影片／方法／提示詞）、常用（importance）、正文。
- 寫入 `知識/<分類>/<名稱>.md`，frontmatter 仍是 `type: collection`（不必新 type，避免遷移地獄）。
- 可選關聯專案：正文加 `[[專案名]]`，不當資料夾巢狀。
- 提示詞繼續用 `category: 提示詞/…`，並可從既有 JSON 匯入。

**測試：** 建立知識的相對路徑、舊 `Collections/*.md` 仍出現在列表、分類篩選。

**完成標準：** 不開 AI、不開 Obsidian，也能在軟體裡寫一篇長期筆記。不要做附件拖曳（Session 6）。

## Session 4 — 任務寫入位置

**現況：** 缺 id 的新任務都追加到收件匣，已掛專案的也常留在收件匣。

**改成：**

- 無專案 → `收件匣/待辦.md`（相容舊 `10-收件匣/待辦收件匣.md`：若舊檔存在且新檔不存在，可繼續寫舊檔，直到搬家）。
- 有專案 → 追加到該專案 `.md` 正文（縮排筆記仍屬該任務）。
- 日曆改時間、看板改狀態：仍改**原檔那一行**，不因為改時間就搬檔。
- 刪專案：專案檔內任務先脫鉤再安全處理（既有 delete 流程要跟著新路徑測）。

**測試：** `buildProjectCreateChange`／`applyDesiredSnapshot` 對有無 `projectId` 的寫入位置；搬動狀態不改 `sourcePath`。

**完成標準：** 打開一個專案檔看得到該專案任務。不要在這次做日誌模板。後來才改專案而搬檔是 Session 9，本 session 不要做。

## Session 5 — 每日日誌

**改成：**

- 當天檔 `日誌/YYYY-MM-DD.md`（沒有就建立）。
- 模板小標：今日會議、結論、產生的任務、可升級的知識。
- 今日畫面可開「今天的日誌」；INDEX 已在 Session 2 指到此路徑。
- 會議仍可當日曆上的一筆任務；**結論**寫日誌，不把整場會議貼進任務行。

**測試：** 跨日不會寫錯檔；既有 `05-每日工作台/YYYY-MM-DD.md` 若存在，讀取相容、新寫入走 `日誌/`。

建議規則：掃描時 `日誌/` 與 `05-每日工作台/` 的 `YYYY-MM-DD.md` 都當日誌；**新建只寫 `日誌/`**。

**完成標準：** 跟 AI 說今天會議時，有一個穩定短檔可寫結論。不要做「自動把日誌全轉知識」。

## Session 6 — 附件（目標用法）

這是「檔案在 `附件/`，md 只有路徑，軟體卻能快速看圖／開檔」的實作 session。

**改成：**

1. 在專案、知識、日誌編輯區：加入檔案或拖曳圖片／PDF。
2. 複製進 vault `附件/<專案或分類>/<原檔名>`；重名則 `-2` 後綴。路徑必須在 canonical root 內。
3. 在該 md 插入相對連結：圖片 `![](...)`，其他 `[檔名](...)`。
4. 預覽：Markdown 預覽用允許的本機協定顯示 vault 內圖片（需新的、受限制的檔案讀取，不能沿用「只准 .md 寫入」的全部假設）。
5. 點 PDF／其他檔：系統預設程式打開。
6. 任務：只允許在該任務縮排筆記裡插入**一個**連結當「做這步要用的檔」；多檔應掛專案或知識。不要每個任務建資料夾。

允許副檔名白名單（建議）：`png jpg jpeg gif webp svg pdf`；可再加 `txt md csv`。拒絕 exe／js／html 當附件。單檔大小上限沿用或低於現有 scan `max_file_bytes`。

`path_policy`：新增「vault 內附件讀取／複製」API，禁止 `..`、symlink、隱藏目錄。掃描 Markdown 時**不要**把 `附件/` 當筆記解析。INDEX **不要**嵌入二進位。

**測試：** 複製後 md 含相對路徑、檔案確實在 `附件/`、vault 外路徑被拒、預覽只接受 vault 內圖片、任務加入第二個檔的政策（拒絕或提示升格）。

**完成標準：** 專案頁加入一張圖，畫面看得到圖；加入 PDF，點一下能打開；磁碟上 md 與 `附件/` 都找得到。不做 PDF 全文抽取。

## Session 7 — 把執行結果存成知識

**改成：**

- 任務詳情／日誌：「存成知識」→ 建 `知識/<分類>/` 新檔，帶來源日期、`[[專案]]`、可選附件連結（複製或沿用已在 `附件/` 的路徑，不要複製兩份除非使用者要）。
- 專案頁「相關知識」：掃描知識正文或 frontmatter 的 wikilink／專案名，列出可開啟的知識。
- 不要自動把打勾的任務變知識。

**測試：** 升級後收件匣／日誌原文仍在；新知識獨立成檔；專案頁連得到。

**完成標準：** 常用／當日／長期三條路都通，且不會再把百科寫進任務行。做完核心必須仍然比現在更簡單，而不是選單更多。

## Session 8 — 本機搬家（不把真實 vault 推進 git）

對象是使用者自己的 Markdown 資料夾。公開 repo 只提供遷移規則與（若需要）App 內「整理成新架構」預覽。

**搬家前：** 既有 ZIP 備份＋校驗；預覽將移動／合併的清單；預設不刪檔。

**規則（檔名盡量不變，以免 `[[wikilink]]` 全斷）：**

| 來源（舊習慣） | 目的 |
| --- | --- |
| `Projects/*.md`、帶 `type: project` 的專案筆記 | `專案/` |
| `Collections/*.md`、提示詞 | `知識/提示詞/` 或依 category |
| `20-學員FAQ/` 等長期筆記 | `知識/<分類>/` |
| `05-每日工作台/YYYY-MM-DD.md` | `日誌/` |
| `10-收件匣/` | `收件匣/` |
| `90-模板/` | `模板/` |
| `99-附件/` | `附件/` |
| 人工總索引（`00-INDEX`、各區「◯◯索引.md」） | 可留作知識或封存；工作地圖改看 `.ai/INDEX.md` |

同一件事若 `Projects/` 與舊分區各一份 `type: project`，預覽時標成重複，讓使用者選正本，不要默默刪。

**完成標準：** 搬家後用軟體新增只落在新資料夾；INDEX 路徑正確；Obsidian 仍能靠檔名打開大多數 `[[連結]]`。產出若含腳本，只用 `examples/` 或測試 fixture，禁止提交真實筆記。

## Session 9 — 改專案就搬走任務那一行

**現況（Session 4 之後）：** 新增時有專案 → 寫進 `專案/<名>.md`；沒專案 → `收件匣/待辦.md`。後來才掛專案或改專案，只改行上的 `[[專案名]]`，人還留在原檔。收件匣會無限長大；打開專案檔看不到後來才歸檔的任務。

**改成：**

| 你做的事 | 檔案 |
| --- | --- |
| 新增、沒選專案 | 寫在 `收件匣/待辦.md` |
| 新增時就選了專案 | 寫在 `專案/那個專案.md`（已有） |
| **後來才改專案／第一次掛上專案** | **整塊搬走**：任務行＋底下縮排筆記＋該任務那一個附件連結 |
| 改成無專案 | 搬回收件匣 |
| 改日期、改狀態、改時間 | **不搬檔**，只改原來那一行 |

規則：

- 同一則任務不要兩份各寫一行。
- 搬家是多檔操作：先備份、原子寫入、recovery journal（既有桌面寫入流程）。
- 保留 id、rank、BOM、CRLF、縮排、未知 token。
- 完成的任務留在專案檔當紀錄，不要自動存成知識。
- INDEX 下次掃描會跟著 `sourcePath` 更新，不必另做 INDEX session。

**測試（先寫失敗測試再改）：**

1. 收件匣任務改掛專案 A → 收件匣那行（含筆記）消失，`專案/A.md` 出現同一 id。
2. 從專案 A 改掛專案 B → A 沒有、B 有。
3. 改成無專案 → 回到 `收件匣/待辦.md`。
4. 只改日期或狀態 → `sourcePath` 不變。
5. 專案檔不存在時不要默默寫到 vault 外；走既有建立／錯誤路徑。

**完成標準：** 打開專案檔看得到後來才歸檔的任務；收件匣只留還沒掛專案的。不要在這次做附件政策、日誌模板或外掛。

## 每個 session 結束時

1. 會改 Markdown／路徑／原生檔案政策：`npm test`；動到 Tauri／`path_policy`：另跑 `npm run rust:test`。
2. 需要時 `npm run build`。
3. 告訴使用者改了什麼、舊 vault 打開要注意什麼。
4. 一次 commit，主題用上表英文句。不要把下一 session 的 diff 塞進來。
5. 開新 session 再做下一項。

## 建議開工順序

```text
1 資料夾契約
    → 2 INDEX
    → 3 知識介面 → 7 存成知識
    → 4 任務寫入位置
    → 5 日誌
    → 6 附件
之後
8 本機搬家
    → 9 改專案就搬走任務行

不做（本計畫）
外掛執行期、主題包引擎、從網路抓知識、外掛商店
```

**一句話：** 生態系很重要，但這個產品的第一個生態是「任何人都能對同一資料夾擴充」。應用內外掛適合當第二個生態，等核心站穩再做；拿它當開源第一張牌，通常換不到套件，只換到更重的核心。
